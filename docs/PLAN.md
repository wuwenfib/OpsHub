# OpsHub 分阶段任务清单

每个任务都写了"目的"和"验收标准"。做完一项：验证 → 打勾 → 总结它对应运维体系里的哪个概念。

---

## 第一阶段：监控链路跑通（工具层 + 对象层）

> 目的：亲眼看到"系统出问题 → 指标异常 → 告警产生"，理解监控体系各组件的分工。

- [x] **1.1 mock-gov-app 模拟系统**
  - 做什么：Go 写一个小 HTTP 服务，有 `/api/apply`（模拟办件接口）、`/healthz`、`/metrics`（请求数、错误数、延迟直方图），以及故障注入接口 `/chaos/slow`、`/chaos/error`、`/chaos/reset`。
  - 学什么：Prometheus 指标的四种类型（Counter / Gauge / Histogram / Summary），应用怎么"暴露"自己的健康状态。
  - 验收：`curl :8081/metrics` 能看到自定义指标；调用 `/chaos/slow` 后延迟指标明显升高。

- [x] **1.2 docker-compose 拉起监控全家桶**
  - 做什么：Prometheus、Alertmanager、Grafana、node_exporter、blackbox_exporter、MySQL + mysqld_exporter、mock-gov-app。
  - 学什么：Prometheus 是"拉"（pull）模型——它主动去各个 exporter 抓数据；exporter 是"翻译官"，把各种系统的状态翻译成统一的指标格式。
  - 验收：Prometheus 的 Targets 页面里所有目标都是 UP。

- [x] **1.3 告警规则**
  - 做什么：写 4 条规则，每条都带 `system` 和 `severity` 标签：
    - 接口 P95 延迟 > 1s 持续 1 分钟（P2）
    - 错误率 > 5% 持续 1 分钟（P2）
    - 探活失败 30 秒（P1）
    - 主机 CPU > 85% 持续 5 分钟（P3）
  - 学什么：告警规则里的 `for` 是为了防抖动；标签决定告警最后被路由到哪里、关联到哪个系统。
  - 验收：执行 `make chaos-slow`，在 Alertmanager 页面看到告警从 pending 变成 firing。

- [ ] **1.4 Grafana 预置看板**
  - 做什么：通过 provisioning 自动配好数据源和一个"系统健康总览"看板（QPS、错误率、P95 延迟、主机资源）。
  - 验收：`make up` 之后打开 Grafana 不需要任何手动配置就能看到图。

## 第二阶段：OpsHub 后端（流程层核心）

> 目的：实现"告警自动变工单，工单带 SLA"，这是整个项目最有价值的部分。

- [ ] **2.1 后端骨架**
  - gin + PostgreSQL + migrate，`/healthz` 可用，加入 docker-compose。
  - 验收：`curl :8080/healthz` 返回 ok；容器重启后数据库迁移自动执行。

- [ ] **2.2 CMDB 增删改查**
  - 厂商、业务系统、主机、系统与主机关系、系统依赖。提供一个 seed 脚本，预置 5 个模拟政务系统（不同等级、不同厂商）。
  - 学什么：CMDB 为什么是运维的"地基"——没有台账，告警来了不知道是谁的、该找谁。
  - 验收：`GET /api/systems/{code}` 能返回系统信息及其主机、厂商、依赖。

- [ ] **2.3 SLA 策略**
  - `sla_policy` 表加种子数据，例如：一级系统 P1 响应 15 分钟、恢复 2 小时；三级系统 P3 响应 4 小时、恢复 3 个工作日（先按自然日简化）。
  - 验收：给定系统等级和严重级别，能算出两个 deadline，并有单元测试覆盖。

- [ ] **2.4 Alertmanager webhook 接入**
  - `POST /api/alerts/webhook`：解析 Alertmanager 的 payload → 按 `system` 标签关联 CMDB → 按 fingerprint 去重 → 新建事件单或追加日志；`resolved` 只记日志、不关单。
  - 学什么：告警 ≠ 工单。告警是机器信号，工单是要人负责的任务；去重和关联是为了避免"告警风暴"把人淹没。
  - 验收：`make chaos-error` 后 1～2 分钟内自动出现一张 P2 事件单，并且关联到正确的系统和厂商；重复告警不会生成重复工单。

- [ ] **2.5 工单状态机与流水**
  - 接口：受理、标记恢复、关闭、重开；非法跳转返回 409；每次变化写 `ticket_log`。
  - 验收：状态机有表驱动单元测试，覆盖所有合法和非法跳转。

- [ ] **2.6 SLA 统计接口**
  - `GET /api/stats/sla?group_by=system|vendor`：故障数、平均恢复时间（MTTR）、响应达标率、恢复达标率、当前超时工单数。
  - 学什么：这就是"用数据考核外包厂商"。
  - 验收：人为制造几次故障后，统计结果和手算一致。

## 第三阶段：前端与演示

- [ ] **3.1 前端骨架**（Vue3 + Element Plus），左侧菜单：系统台账、工单、SLA 看板。
- [ ] **3.2 系统台账页**：列表、详情（主机、厂商、依赖关系）。
- [ ] **3.3 工单页**：列表（超时标红）、详情（流水时间线）、状态操作按钮。
- [ ] **3.4 SLA 看板**：按系统、按厂商的达标率与 MTTR 图表（ECharts）。
- [ ] **3.5 演示脚本** `docs/DEMO.md`：5 分钟能讲完的演示流程——注入故障 → Grafana 看到异常 → 自动生成工单 → 处理并关单 → 看板上厂商达标率变化。

## 第四阶段（可选加分）：AI 运维助手

- [ ] **4.1 运维知识库**：把系统文档和已关闭工单的处置记录做 Embedding，存进 pgvector。
- [ ] **4.2 相似故障推荐**：新事件单生成时，检索历史上相似的工单，在详情页展示"类似故障曾这样处理"。
- [ ] **4.3 问答**：在工单页提问，用 RAG 回答（模型可接本地 Ollama 或 API，做成可配置）。
- 学什么：在政务私有化场景里 AI 怎么落地才实在——数据不出内网、只做辅助建议、不自动执行操作。
