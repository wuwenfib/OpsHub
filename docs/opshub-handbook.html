OpsHub 实现手册

一个小型 IT 运维管理平台，用来跑通政企运维的核心链路：系统出故障，监控自动发现，生成带 SLA 时限的工单并找到责任厂商，厂商按流程处理，考核数据自动更新。

项目背景是 200 个左右的业务系统从各厂商划转过来后的管理问题：台账怎么建、告警怎么变成任务、怎么用数据考核外包厂商。这是学习型 Demo，目标是能一键拉起、现场演示，并且能讲清楚每一层为什么这样设计。

15 / 15前三阶段任务完成（第四阶段 AI 助手可选，未做）
≈2000后端手写 Go 代码行数
≈1250sqlc 生成的 Go 代码行数
≈1500后端测试代码行数
8业务表（3 个迁移文件）
93 秒实测：注入故障到自动建单

整体架构

原则只有一条：采集、存储、告警计算全部用开源组件，自己只写"管理"那部分。下面绿色的两层是自己写的。

被管对象层
mock-gov-app（Go，模拟政务系统，暴露 /metrics，可注入慢、报错、宕机）和 MySQL（被监控的业务库）
工具层
node_exporter、mysqld_exporter、blackbox_exporter → Prometheus（存储、告警规则）→ Alertmanager（分组、抑制、路由）；Grafana 看图
流程层
OpsHub 后端（Go 单体 + PostgreSQL 16）：CMDB、告警接入、工单状态机、SLA 计时与统计。入口是 Alertmanager 的 webhook
展示层
OpsHub 前端（Vue3 + Element Plus + ECharts）：系统台账、工单、SLA 看板，只消费 REST API

两个数据库职责不同：MySQL 只是"被看的对象"，PostgreSQL 是"平台自己的账本"，两者互不相干。

后端实现

分层与代码组织

后端的核心设计是把判断逻辑和读写数据库分开。状态机怎么转、截止时间怎么算、告警该建单还是记日志，都是不碰数据库的纯函数，用表驱动测试就能覆盖全部分支；事务和 SQL 集中在 service 和 store 两层。依赖方向只能从上往下。

api/        gin handler：解析请求 → 调 service → 错误映射为 HTTP 状态码
service/    用例编排：开事务 → 调纯逻辑 → 读写库
cmdb/  ticket/  sla/  alert/    纯领域逻辑，零 IO，可单测
store/      手写 SQL + sqlc 生成的查询函数 + 事务封装
apperr/     跨层共用的哨兵错误（最底层，谁都能引用）
包行数职责关键内容
cmd/opshub78进程入口连库 → 迁移 → 组装依赖 → 启动 HTTP → 收到 SIGTERM 优雅退出
internal/api443HTTP 层路由、handler，writeError 是唯一的错误出口
internal/service777用例编排CMDB、Alerts、Tickets、Stats，Clock 接口
internal/alert108纯逻辑Parse 解析 payload，Decide 决定动作
internal/ticket109纯逻辑Transition 状态表，Apply 计算字段变化
internal/sla195纯逻辑DeadlinesFrom、Evaluate、Aggregate
internal/cmdb150纯逻辑输入规范化与校验（编码格式、等级、IP）
internal/store138数据访问Connect、Migrate、InTx、MapError（另有 1246 行生成代码）
internal/apperr12错误定义4 个哨兵错误

数据访问用 sqlc + pgx：在 queries/*.sql 里手写 SQL，sqlc 读取迁移文件得到表结构，生成带类型的 Go 函数。SQL 写错列名时，生成代码这一步就会报错。没有选 ORM，是因为隐式生成的 SQL 出问题时很难看清发生了什么。

internal/store/queries/ticket.sql
-- name: GetTicketForUpdate :one
SELECT * FROM ticket WHERE id = $1 FOR UPDATE;

事务封装只有几行。传入的函数正常返回就提交，返回错误或发生 panic 就回滚，调用方不可能忘记回滚，作用类似 C++ 的 RAII 事务守卫。

internal/store/store.go
func (s *Store) InTx(ctx context.Context, fn func(q *Queries) error) error {
	return pgx.BeginFunc(ctx, s.pool, func(tx pgx.Tx) error {
		return fn(s.Queries.WithTx(tx))
	})
}

实现过程

后端按 6 个任务小步推进，每个任务一个 commit，每一步都先验证再打勾。

2.1

后端骨架

先立起能启动、能连库、能自动迁移的空架子。启动顺序是连库（每秒重试，最多 30 次）→ 执行迁移 → 对外服务。迁移 SQL 通过 go:embed 编进二进制，运行镜像是 scratch，里面只有一个可执行文件。

cmd/opshub/main.go
pool, err := store.Connect(ctx, dbURL)    // 带重试，等数据库就绪
if err := store.Migrate(dbURL); err != nil { ... }

st := store.NewStore(pool)
router := api.NewRouter(api.Deps{
	DB:      pool,
	CMDB:    service.NewCMDB(st),
	Alerts:  service.NewAlerts(st, service.RealClock{}),
	Tickets: service.NewTickets(st, service.RealClock{}),
	Stats:   service.NewStats(st, service.RealClock{}),
})

健康检查只依赖一个接口 Pinger，数据库不可达时返回 503。*pgxpool.Pool 不用声明就自动满足它，单测里传一个假实现即可。

验证：空库从零迁移成功；重复执行不报错；停掉 PostgreSQL 后 healthz 返回 503，恢复后连接池自动重连回到 200。

2.2

CMDB 增删改查

建立厂商、系统、主机及其关系的接口。系统编码格式收得很紧（大写字母开头，只含大写字母、数字、连字符，2～32 位），因为它要和告警的 system 标签逐字相等。IP 用 netip.ParseAddr 规范化，避免同一地址的不同写法绕过唯一约束。

"整体替换关系"接口在一个事务里先清空再插入，中途失败就整个回滚。依赖编码不存在时，报错会列出具体是哪几个。

internal/service/cmdb.go（节选）
n, err := q.AddSystemDependencies(ctx, params)
...
if int(n) != len(codes) { // 有编码没匹配上：报给调用方，事务回滚
	return fmt.Errorf("%w: 依赖的系统不存在: %s", apperr.ErrValidation,
		strings.Join(missing(codes, detail.DependsOn), ", "))
}

验证：GET /api/systems/GOV-APPLY 一次返回厂商、3 台主机和上下游依赖；集成测试确认替换失败后原关系不变。

2.3

SLA 策略

12 行策略放在迁移里，它们是系统运行的前提。sla 包只做纯计算，查询函数接收 *store.Queries，这样既能走连接池，也能和建单放进同一个事务。

internal/sla/sla.go
func (p Policy) DeadlinesFrom(createdAt time.Time) Deadlines {
	start := createdAt.UTC()
	return Deadlines{Response: start.Add(p.Response), Resolve: start.Add(p.Resolve)}
}

验证：集成测试逐条核对 12 行策略；主库在有数据的情况下从 version 1 增量升级到 version 2，原有数据保留。

2.4

Alertmanager webhook 接入

这是整条链路的核心，详见下文告警到工单。除 payload 无法解析（400）外一律返回 200，响应体带处理统计，避免 Alertmanager 整批重试。

验证：make chaos-error 后第 96 秒自动生成 P2 单，关联到 GOV-APPLY 和星河软件；重放真实告警不重复建单；chaos-reset 后第 95 秒收到恢复通知，工单状态不变。

2.5

工单状态机与流水

实现受理、恢复、关闭、重开四个操作，每次变化写流水，非法跳转返回 409。顺带完成手工建单和按状态、按系统筛选。详见工单状态机。

验证：5 种状态 × 4 种动作共 20 种组合全部有表驱动测试；20 个并发的关闭和重开恰好 1 个成功。

2.6

SLA 统计接口

GET /api/stats/sla 按系统或厂商统计。先用 SQL 取出时间范围内的事件单，再在 Go 里用纯函数汇总，这样能直接用手算案例写单测。工单详情和列表也带上 SLA 状态，支持 overdue=true 筛选。详见SLA 计算。

验证：制造真实故障后，用独立的 Python 脚本只读原始时间字段重新计算，和接口逐项对比，0 处不一致。

告警到工单

Alertmanager 一次推送可能带多条告警，每条告警一个独立事务，一条失败只记日志，不影响同批其他告警。

sequenceDiagram
    participant AM as Alertmanager
    participant API as api
    participant A as alert 纯逻辑
    participant S as service.Alerts
    participant DB as PostgreSQL
    AM->>API: POST /api/alerts/webhook
    API->>A: Parse 解析请求体
    A-->>API: Payload 或 400
    loop 每条告警一个事务
        API->>S: handleOne
        S->>DB: 按 fingerprint 查未关闭工单
        S->>A: Decide 决定动作
        alt firing 且无工单
            S->>DB: 查 CMDB 和 SLA 策略
            S->>DB: INSERT ON CONFLICT DO NOTHING
            S->>DB: 写 created 流水
        else firing 且有工单
            S->>DB: 写 duplicate_alert 流水
        else resolved 且有工单
            S->>DB: 写 alert_resolved 流水，不关单
        else resolved 且无工单
            S-->>API: 忽略
        end
    end
    API-->>AM: 200 和处理统计

决策本身是一个纯函数：

internal/alert/alert.go
func Decide(a Alert, hasOpenTicket bool) Action {
	switch {
	case a.Status == StatusFiring && !hasOpenTicket:
		return CreateTicket
	case a.Status == StatusFiring:
		return AppendDuplicate
	case hasOpenTicket:
		return AppendRecovered
	default:
		return Ignore
	}
}

并发去重

"先查有没有，没有再插入"在并发下有竞态：两个请求可能都查到"没有"，然后各建一张单。所以把"同一指纹最多一张未关闭工单"这条不变量交给数据库保证，思路和用 CAS 取代先读后写一样。

migrations/000003_ticket.up.sql 与 queries/ticket.sql
CREATE UNIQUE INDEX ticket_open_fingerprint_uq
    ON ticket (alert_fingerprint) WHERE status <> 'closed';

INSERT INTO ticket (...) VALUES (...)
ON CONFLICT (alert_fingerprint) WHERE status <> 'closed' DO NOTHING
RETURNING *;

冲突时 RETURNING 不返回行，sqlc 生成的函数得到 pgx.ErrNoRows。代码据此退回"追加重复日志"分支：

internal/service/alert.go
created, err := s.createTicket(ctx, q, a, now)
if err != nil {
	return err
}
if created {
	return nil
}
// 并发冲突：另一个请求刚为同一指纹建了单。按"重复告警"处理。
act = alert.AppendDuplicate
if open, err = q.GetOpenTicketByFingerprint(ctx, fingerprint); err != nil {
	return err
}
return appendLog(ctx, q, open.ID, "duplicate_alert", duplicateNote(a), now)

索引只覆盖未关闭的工单，所以关单后同一告警再次触发会新建工单：一张单就是一次故障，统计口径最清楚。

建单时的默认口径

  • system 关联不上 CMDB：system_id 为 NULL，原始值存入 system_label，按二级系统计算 SLA，并写入流水。
  • severity 缺失或非法：按 P3 处理，并写入流水。
  • 工单标题优先用规则的 summary 注解，没有就用"告警名 [系统]"。

工单状态机

只实现事件单（incident）的状态机。问题单和变更单可以手工创建，但不能流转。

stateDiagram-v2
    [*] --> new: 建单
    new --> acknowledged: ack 受理
    acknowledged --> resolved: resolve 标记恢复
    resolved --> closed: close 确认关闭
    resolved --> reopened: reopen 重开
    reopened --> resolved: resolve 标记恢复
    closed --> [*]

状态机就是一张查找表，表里没有的组合都是非法跳转。new 不能直接跳到 resolve，因为 SLA 要单独考核响应这一步。

internal/ticket/ticket.go
var transitions = map[Status]map[Action]Status{
	New:          {Ack: Acknowledged},
	Acknowledged: {Resolve: Resolved},
	Reopened:     {Resolve: Resolved},
	Resolved:     {Close: Closed, Reopen: Reopened},
}

func Apply(s Snapshot, act Action, operator string, now time.Time) (Snapshot, error) {
	...
	switch act {
	case Ack:
		out.RespondedAt = &now // 响应时间 = 受理时间，用于考核响应 SLA
		out.Assignee = operator
	case Resolve:
		out.ResolvedAt = &now
	case Close:
		out.ClosedAt = &now
	case Reopen:
		out.ResolvedAt = nil   // 没修好：清空恢复时间，以最后一次恢复为准
	}
	return out, nil
}

service 层把它们串进一个事务：先用 SELECT ... FOR UPDATE 锁住这一行，再判断和写入。两个人同时操作时会排队，后到的看到的是新状态。

internal/service/ticket.go
err := s.st.InTx(ctx, func(q *store.Queries) error {
	cur, err := q.GetTicketForUpdate(ctx, id)      // 锁行
	...
	next, err := ticket.Apply(snapshotOf(cur), act, operator, now)  // 纯逻辑
	...
	q.UpdateTicketState(ctx, ...)                  // 写回
	return q.InsertTicketLog(ctx, ...)             // 记流水
})

SLA 计算

建单时就把两个截止时间写进工单，之后修改策略也不影响已有工单的考核口径。判断是否超时只需要比较当前时间和截止时间，不需要定时任务。

"是否达标、是否超时"只在 sla.Evaluate 里定义一次，统计、详情、超时筛选都调用它。每个时限只有三种结果：

internal/sla/sla.go
func judge(doneAt *time.Time, deadline, now time.Time) (met *bool, overdue bool) {
	switch {
	case doneAt != nil:
		ok := !doneAt.After(deadline)
		return &ok, false
	case now.After(deadline):
		no := false
		return &no, true    // 还没做完但已过期：确定违约
	default:
		return nil, false   // 还没做完也没过期：待定
	}
}
指标算法
故障数时间范围 [from, to) 内创建的事件单数量
MTTR已恢复工单 resolved_at - created_at 的平均值，单位分钟
响应达标率达标数 ÷ 已有结论的工单数。待定的单不计入分母
恢复达标率同上，看最后一次 resolved_at。重开会清空它，所以假修好会被如实计入
当前超时数现在仍未响应且已过响应截止，或仍未恢复且已过恢复截止

分母为 0 时比率返回 null，表示"还没有结论"，和 0% 的"全部违约"区分开。当前实现在 Go 里汇总，到几十万张工单的规模时应改为 SQL GROUP BY。

错误处理

Go 的错误是普通返回值。领域层用 %w 包装 4 个哨兵错误，错误信息带具体原因，同时保留类型；api 层用 errors.Is 统一翻译，中间包了几层都能识别。500 的详情只写日志，不返回给客户端。

internal/api/errors.go
func statusOf(err error) (int, string) {
	switch {
	case errors.Is(err, apperr.ErrNotFound):
		return http.StatusNotFound, "not_found"
	case errors.Is(err, apperr.ErrValidation):
		return http.StatusBadRequest, "validation"
	case errors.Is(err, apperr.ErrConflict):
		return http.StatusConflict, "conflict"
	case errors.Is(err, apperr.ErrInvalidTransition):
		return http.StatusConflict, "invalid_transition"
	default:
		return http.StatusInternalServerError, "internal"
	}
}

数据库错误由 store.MapError 翻译：无行 → NotFound，唯一约束（23505）→ Conflict，外键（23503）和 CHECK（23514）→ Validation。错误体统一为 {"error": "...", "code": "..."}。

验证测试本身有效

并发测试最初是假的。我把 FOR UPDATE 去掉后测试照样通过，查下来有两个原因：goroutine 启动有先后；连接池是懒创建的，新建连接要几毫秒，比事务本身还慢，请求被"等连接"这一步无意中串行化了。修法是加起跑线 channel，并在起跑前预热连接池。

场景没有保护有保护
20 个并发的关闭和重开去掉行锁：16 个"成功"，数据被改乱恰好 1 个成功，19 个返回 409
20 个并发推送同一告警—只建 1 张单，每次约 15 个请求真正撞上唯一索引

设计取舍

决定原因
未登记系统用 system_id = NULL 加 system_label，不建占位系统占位记录会混进台账列表和"按系统统计"。NULL 自然单独成组，还能提示台账不全
工单上存 deadline，不每次按策略现算策略改了也不影响已有工单，相当于按签约时的条款执行；判断超时不需要定时任务
用部分唯一索引做去重只约束未关闭工单，既挡住并发重复建单，又允许关单后的同一告警新建工单
closed 是终态，重开只能从 resolved 发起一张单就是一次故障，MTTR 和达标率的口径最清楚
重开清空 resolved_at，历史留在流水工单表存当前事实，流水表存全过程。恢复考核以最后一次为准
枚举用 TEXT + CHECK比 PostgreSQL 的 ENUM 类型容易通过迁移修改，sqlc 映射成普通字符串也简单
sla_policy 进迁移，演示数据进 seed策略是系统运行的前提；演示系统和历史工单删了也不影响运行
删除厂商或系统时置空，不级联删工单考核历史不能因为台账变动而消失

监控侧

mock-gov-app 暴露三个指标：http_requests_total（Counter）、http_request_duration_seconds（Histogram，桶密集覆盖 1 秒附近）、gov_app_chaos_mode（Gauge）。它自带流量发生器，否则错误率的分母是 0，告警永远不会触发。

system 标签打在 Prometheus 的抓取配置里，没有写进应用代码。真实环境里被管系统的代码往往改不动，归属关系只能由运维侧标注。

Alertmanager 按 [alertname, system] 分组（group_wait 10s、group_interval 1m、repeat_interval 4h），并配置抑制：同系统探活失败时，抑制延迟和错误率告警。规则有 promtool 单元测试，Grafana 的数据源和"系统健康总览"看板通过 provisioning 自动加载。

前端

页面内容
系统台账列表支持搜索、等级筛选，顶部提示未登记的告警来源。详情含厂商（合同到期提醒）、主机、上下游依赖、在办工单
工单列表可筛选，超时整行标红，每 30 秒刷新，可手工建单。详情含两个时限的倒计时、流水时间线、当前状态允许的操作按钮
SLA 看板指标卡、达标率图（含 90% 示例考核线）、MTTR 图、明细表。可按厂商或系统分组，可选日期范围

前端的 allowedActions 只决定显示哪些按钮，真正的规则在后端。两边不一致时后端返回 409，页面刷新到最新状态并说明原因。

已知简化

  • 前端没有进 docker-compose，需要另外执行 make web。
  • 台账没有编辑界面，增删改要调 API。
  • 问题单和变更单只能建单，不能流转。
  • 没有登录和权限，操作人由调用方填写。
  • SLA 按自然时间计算，不扣除节假日和非工作时间。
  • 统计在 Go 里汇总，列表最多返回 200 条，只适合演示规模。
  • HostHighCPU 只有规则单元测试，没有用真实负载触发过。
  • 抑制规则只用模拟告警验证过：真实宕机时指标消失，延迟告警会自行恢复，走不到抑制。
  • 前端没有自动化测试，页面是在浏览器里手动验证的。
