# OpsHub 5 分钟演示脚本

**要讲清楚的一句话**：系统出故障 → 监控自动发现 → 自动生成带 SLA 时限的工单、找到责任厂商 → 厂商按流程处理 → 考核数据自动更新。

下文的时间点都是 2026-10-30 实际彩排测得的结果（`T+` 表示距离注入故障的秒数）。其中最长的一段空档是"等告警确认"，大约 90 秒，这段时间正好用来讲监控链路。

---

## 一、演示前准备（提前 10 分钟）

```bash
make up            # 启动全部容器
make seed          # 台账 + 过去 30 天的 11 张历史工单（可重复执行）
make web           # 另开一个终端：前端 :5173
```

如果希望看板只显示历史数据、不留之前测试的痕迹，执行下面的命令（**会删除全部工单**，台账保留，会要求输入 yes 确认）：

```bash
make demo-reset
```

最后自检，确认 6 个服务都是 ✓、firing 告警数为 0、故障注入模式为 0：

```bash
make demo-check
```

**按顺序打开 4 个浏览器标签页**（`demo-check` 会打印实际地址，Grafana 端口以它为准）：

| # | 页面 | 地址 |
|---|---|---|
| 1 | OpsHub SLA 看板 | http://localhost:5173/sla （切到"按厂商"） |
| 2 | Grafana 系统健康总览 | http://localhost:3000/d/opshub-system-health （本机为 3002） |
| 3 | Prometheus 告警 | http://localhost:9090/alerts |
| 4 | OpsHub 工单 | http://localhost:5173/tickets |

**记下第 1 页上星河软件的数字**，演示结尾要用来对比。执行过 `demo-reset` 的话，数字应该是：

| 厂商 | 故障数 | 响应达标率 | 恢复达标率 | MTTR |
|---|---|---|---|---|
| 星河软件 | 4 | 50%（2/4） | 75%（3/4） | 3 小时 6 分 |

## 三、备用演示（时间富余或被追问时）

**告警去重**：拿到真实告警的指纹后，原样重放给 webhook，工单数不变，流水里多一条"告警重复推送"。

```bash
curl -s localhost:9093/api/v2/alerts | python3 -c 'import json,sys; print([a["fingerprint"] for a in json.load(sys.stdin)])'
```

**宕机与抑制**：执行 `make chaos-down`，约 60 秒后生成一张 **P1** 探活失败单。演示完执行 `make chaos-reset` 恢复。

**重开**：在一张"已恢复"的工单上点"重开"，恢复时间会被清空，最终以下一次恢复为准。"假修好"会被如实计入恢复时长。

**并发冲突**：开两个浏览器标签页打开同一张工单，在一边点"确认关闭"，在另一边点"重开"。后提交的一边会提示"操作未执行：工单当前状态为……"。

**未登记系统**：系统台账页顶部的黄色提示，以及看板上的"未关联厂商"分组，都说明还有告警关联不上台账，需要补录。

## 四、常见追问

**为什么只做管理那一层，不自己写监控？**
采集、存储、告警计算都是成熟的开源组件，自己重写既没有优势，也不好维护。真正因单位而异的是管理流程：台账、考核口径、责任划分，这部分才值得自己写。

**告警怎么和台账关联起来？**
在 Prometheus 的抓取配置里，给每个目标打上 `system` 标签，值等于台账中的系统编码。被管系统的代码通常改不了，所以归属关系由运维侧来标注。关联不上的告警照样建单，按二级系统计算 SLA，并在台账页和看板上提示。

**并发推送同一个告警，怎么保证只建一张单？**
在数据库上建部分唯一索引 `UNIQUE(alert_fingerprint) WHERE status <> 'closed'`，插入时用 `ON CONFLICT DO NOTHING`，冲突了就改为追加一条流水。如果在代码里"先查再插"，并发时两个请求可能都查到"没有"，就会各建一张。集成测试里 20 个并发请求只会建出 1 张单。我还专门验证过：把唯一索引拿掉，测试确实会失败。

**两个人同时操作同一张工单呢？**
在事务里用 `SELECT ... FOR UPDATE` 锁住这一行，先判断状态机能不能这样跳转，再写入。测试里 20 个并发的"关闭"和"重开"只有 1 个能成功。去掉行锁的话，会有 16 个"成功"。

**超时怎么判断？用定时任务吗？**
不用。建单时就把两个截止时间写进工单，查询时拿当前时间和截止时间比较。之后即使修改 SLA 策略，也不会影响已有工单的考核口径，相当于"按签约时的条款执行"。

**达标率的分母怎么算？**
只统计"已有结论"的工单。还没处理、但也还没到截止时间的单不计入分母。否则月底统计时，正在处理中的单会让达标率失真。

**为什么告警恢复了不自动关单？**
指标恢复正常，不代表问题真的解决了。由人确认后关单，"恢复时间"这个考核数据才可信；如果没修好，还可以重开。

**数据量大了怎么办？**
目前统计是先把工单取到 Go 里再汇总，好处是汇总逻辑可以直接用手算案例做单元测试。到了几十万张工单的规模，应该改成 SQL `GROUP BY`，或者按天预先聚合。

## 五、收尾与排错

演示结束后执行 `make chaos-reset`，然后用 `make demo-check` 确认 firing 告警数为 0、故障注入模式为 0。

| 现象 | 排查 |
|---|---|
| 超过 2 分钟还没出工单 | 到 Prometheus 页面看告警是否 firing；用 `make logs s=alertmanager` 看推送是否成功；用 `make logs s=opshub` 看 webhook 是否收到请求 |
| 前端右上角显示"后端不可用" | `make ps` 查看 opshub 容器状态 |
| Grafana 打不开 | 端口被占用时，在 `deploy/.env` 里设置 `GRAFANA_PORT`，以 `make demo-check` 打印的地址为准 |
| 上一次演示的告警还在 firing | 执行 `make chaos-reset`，等待 1～2 分钟告警自然恢复 |
